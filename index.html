1. Enterprise Insurance RAG AssistantGuarded, cached two-stage RAG with durable memory and evals2025–2026

Problem

Policy questions were answered by hand. A usable assistant had to answer from approved documents, refuse unsafe or off-topic input, stay fast, and keep LLM spend predictable.

Solution

A guarded, cached, two-stage retrieval RAG service with durable conversation memory, automatic model fallback and a repeatable evaluation suite.

My role

Designed and implemented the architecture end to end: ingestion, retrieval and reranking, guardrails, cache, memory, gateway, evals and Terraform deployment.

Request flow

User query→NeMo Guardrails
Llama 3.1 8B→Redis semantic cache
cos < 0.15→LangGraph planner
70B→Qdrant top-15
768-dim→FlashRank
top-5→Responder
70B via Portkey→Answer

How each piece works

OrchestrationLangGraph state machine: planner → retriever → responder. The planner returns either CONVERSATIONAL (skip retrieval) or a refined search query, so greetings and follow-ups avoid an embedding and vector round-trip.
GuardrailsNVIDIA NeMo Guardrails with Colang rules (jailbreak, off-topic, greeting, capabilities) on Llama 3.1 8B via Groq. A fired rail returns before the graph runs, so blocked traffic never reaches the 70B model.
Semantic cacheQuery embedded with Vertex AI text-embedding-004; Redis entries compared by cosine distance (< 0.15), 1-hour TTL. Linear key scan is fine at this scale; a vector index would replace it at higher volume.
RetrievalQdrant dense search returns the top 15 chunks, then a local FlashRank ONNX cross-encoder reranks to the top 5. Wide recall first, precise context second, which keeps the prompt small.
LLM gatewayPortkey config: Llama 3.3 70B primary, Llama 3.1 8B fallback, 2 retries on 429/503. Provider rate limits degrade answer quality instead of causing outages.
MemoryLangGraph PostgresSaver on Cloud SQL, keyed by thread_id, so conversation state survives Cloud Run restarts and scale-to-zero. MemorySaver is used in local mode.
IngestionGCS raw bucket → Eventarc → Cloud Run. Google Document AI parses PDFs, text is split into ~1,500-character chunks, embedded and upserted into Qdrant. A separate processed bucket prevents trigger loops.
Evals & observabilityRAGAS (faithfulness, answer relevancy, context precision and recall, answer correctness) plus guardrail TP/FP/FN. LangSmith traces LLM calls; Pydantic Logfire spans the application workflow.
InfrastructureTerraform-defined Cloud Run services (API, Streamlit UI, evals, ingestion), Cloud SQL, Memorystore Redis and VPC; deployed with Cloud Build.

2. E-commerce AI Shopping AssistantTool-calling agent with parallel input guards and span-based evals2025–2026

Problem

Shoppers had to apply several filters by hand. A chat assistant also needed protection from prompt injection and unsafe replies without slowing every message.

Solution

A tool-calling agent that turns natural language into a structured product search, wrapped in parallel input guards and an output policy check.

My role

Built the agent, search tool, two-sided guardrails, evaluation suite and Cloud Run deployment.

Request flow

Chat message→Prompt Guard 2 ‖
gpt-oss-safeguard-20b→Pydantic AI agent
gpt-oss-20b→search_products
tool→MongoDB→Output safeguard→Products / text

How each piece works

Agent & toolPydantic AI agent with a typed search_products tool (category, keyword, min/max price). The tool builds a MongoDB regex query, returns at most 8 products, and passes them to the UI through a dependency object, so the LLM only writes a short confirmation.
Input safetyLlama Prompt Guard 2 (86M, blocks at score ≥ 0.5) and gpt-oss-safeguard-20b (policy-as-prompt, JSON verdict) run in parallel with asyncio.gather, so added latency is the slower check, not the sum.
Output safetyA second safeguard pass checks the reply against an output policy (prompt leakage, unauthorized promises, unsafe content). Guards fail open on provider errors, trading strictness for availability.
GatewayOptional Portkey routing and logging in front of Groq; the app falls back to direct Groq calls when no Portkey key is set.
EvalsPydantic Evals suite (10 cases): span-based checks that the search tool was actually called (catches replies claiming “no results” without searching), guardrail block/no-over-block cases, and an LLM judge. Online evals are optional and sampled at 30%.
DeploymentSingle FastAPI + JS app on Cloud Run (asia-south1), built with Cloud Build, secrets in Secret Manager, traces in Logfire.

Cost profile

Prompt Guard 20 $
Input safeguard0.084 $
Agent call 10.084 $
Agent call 20.075 $
Output safeguard0.086 $
Estimated $ per 1,000 chats (≈ $0.0003 each).

Outcomes

Faster discovery

One sentence replaces multi-filter navigation; results render as product cards.

Safe by design

Input and output checks run with policy prompts, and guard latency is the slower check, not the sum.

Tested tool use

Span-based evals verify the search tool really ran, which exposes hallucinated “no results”.

3. AI-Based ServiceNow Ticket Triaging SystemRandom Forest workflow that classifies, prioritizes and routes ticketsSungard Availability Services · 2021–2023

Problem

Every incoming ServiceNow ticket was read by an L1 engineer, who identified the issue and picked the assignment group by hand. This caused slow assignment, wrong-team routing and reassignments, inconsistent prioritization and SLA breaches.

Solution

An end-to-end machine learning workflow that classifies, prioritizes and automatically routes tickets using a Random Forest model, integrated with ServiceNow through its REST API.

My role

As Data Scientist, I designed and deployed the workflow: data preparation, feature engineering, model training, hyperparameter tuning, evaluation, ServiceNow integration and deployment on AWS EC2.

Workflow

ServiceNow incident→REST API→Python ingestion
+ preprocessing→Random Forest
classify · prioritize · route→Prediction validation→REST API update→Assigned support team

How each piece works

Training dataAbout five years of historical ServiceNow tickets with known outcomes served as labelled examples. Records were cleaned (missing values, duplicates, inconsistent categories) and encoded into numeric, model-ready features.
ModelRandom Forest: an ensemble of decision trees whose votes are combined for multiclass routing. It generalizes better than a single tree, models non-linear relationships and suits structured ticket data.
Tuning & evaluationHyperparameters were tuned and the model evaluated with precision and F1-score, which matter because a wrong prediction sends an incident to the wrong team.
IntegrationThe ServiceNow REST API supplies new incidents to the Python service and receives the predicted routing back on the ticket, so tickets reach the right group without manual review.
DeploymentPython service hosted on AWS EC2.
MaintenanceRetrained every three months so the model keeps up with changing ticket patterns and newly created assignment groups.

Reported results

L1 support effort−95%
SLA breaches−25%
Reduction versus the manual process.

Outcomes

Less manual triage

L1 engineers no longer review and route every ticket by hand.

Faster, more consistent routing

Tickets are classified and prioritized the same way every time, reducing delays and reassignments.

Fewer SLA breaches

Quicker assignment brought SLA breaches down by 25%.
